    Cross-team findings from the 2026-07-13 docs review

    This document summarizes findings from the docs review of all five Virtufin docs sites (api, workmanager, websocketmanager, specs, lib) that the worker repo can't fix on its own. Each finding lists the owning repo, the concrete remediation, and the priority.

    The worker repo (virtufin-workers) addressed its in-scope items directly:

    • Dropped the vestigial group field from WebSocketManagerController/config/config.json (commit d8e018f).
    • Added the in-process crash isolation caveat to WebSocketManagerControllerNative.cs (commit d8e018f).
    • Renamed the managed project to …Managed/ and the AOT sibling to …Native/, both producing a nupkg with the same <PackageId>Virtufin.Worker.WebSocketManagerController</PackageId> (commit ce815ef).
    • Replaced the --format flag with three orthogonal build entry points: build_managed.py, build_aot.py, build_both.sh (commit 06fb5a0).

    The items below are for the maintainers of the other repos to triage.

    virtufin-workmanager

    Priority Finding Remediation
    P0 The Group field removal from CreateWorkerRequest (proto regen commit c21933f) was not announced in a release note or migration guide. A deployed worker that previously sent a group parameter now silently behaves differently (no more group-lock mutual exclusion — replaced by competing-consumer semantics per the horizontal-scalability spec). Add a CHANGELOG entry under the 0.3.4 release (or whichever release carried the group-removal) calling out the breaking change. Update the Architecture page or add a Migration section describing "what changed and how to verify" — the new model is the competing-consumer model from the horizontal-scalability requirement, not the old group-lock model.
    P1 NativeDllEngine loads native shared libraries in-process with no sandbox. The Security page documents Python sandboxing and C# in-process risks but says nothing about native DLL workers. Add a prominent warning: "native DLL workers have root-equivalent access to the host process and should only be used with fully trusted, signed artifacts." The worker repo's WebSocketManagerControllerNative.cs class docstring now references this; mirror it in the WM's security page.
    P2 The docker-compose.yml in the integration guide has port collisions — all three services are mapped to 5001/5002 on the host. Use distinct host port ranges per service (e.g. 5001/5002 for API, 5011/5012 for WM, 5021/5022 for WSM).
    P2 The Dapr minimum version requirement is not stated on the WM site (only the API site says 1.18+). Add a "Prerequisites" or "Deployment requirements" section calling out Dapr 1.18+ as the minimum.
    P2 The horizontal-scalability statement "multiple WorkManager replicas on the same topic COMPETE, not load-share" is in the specs site but not in the WM operator-facing docs. Add a "Scaling" section in the operations page that reproduces this — operators will be surprised by the behavior otherwise.
    P3 "Stuck-recovery" state-store corruption: if the state store contains a bad worker entry that always fails to load, the pod is permanently unready. Add a WORKER_SKIP_FAILED_WORKERS=true flag (skip-on-load-error) or an admin gRPC endpoint to delete individual state-store entries. Document in the recovery section.
    P3 Worker recovery error handling: "if recovery fails entirely, the health check reports Unhealthy and the pod will not become ready" — correct, but no documented recovery path from a failed recovery. Same as above.

    virtufin-websocketmanager

    Priority Finding Remediation
    P1 AllowedCodeSourceHosts key in the WebSocketManager security configuration table with the note "Not applicable — WebSocketManager does not fetch worker code." This key shouldn't be in the table at all for this service. Remove the row from the WSM security page's configuration table. Operators seeing it will wonder why a worker-code config key is listed in a WebSocket service.
    P2 SendAndWaitAsync documentation has zombie steps (2-6) that contradict the correct binary UUID prefix description immediately above them. Delete the zombie steps; keep only the binary UUID description. The Send/Receive docs should match the actual code path.
    P2 SendRawAsync documentation shows string as the message parameter type, but the interface definition shows byte[]. The prose and the interface are inconsistent. Fix the prose to byte[] message (or whatever the actual interface is).

    virtufin-api

    Priority Finding Remediation
    P0 Reflection cache TTL (P2-1): ServiceDescriptorCache is described as lazily loaded and thread-safe, but no TTL, no invalidation endpoint, no mention of what happens when a backend service redeploys with a changed proto schema. The gateway will silently serve stale descriptors until it restarts. Add a TTL (e.g. 5 min, configurable) and an explicit invalidation endpoint (Gateway.InvalidateCache(serviceName) or Gateway.RefreshSchema(serviceName)). Document the staleness window.
    P1 The GrpcChannelPool section appears verbatim twice in the Services page. Duplicate section has survived every review. Find-and-replace the duplicate include or the duplicate nav entry in docs/v1/mkdocs_v1.yml. The duplicate is at the source-file level.
    P2 The Dapr minimum version requirement (1.18+) is stated on the API site but not on the WM or WSM sites. Cross-link from the WM/WSM sites to the API's Dapr version requirement (or duplicate the statement in each).

    virtufin-dotnet (lib.docs.virtufin.com)

    Priority Finding Remediation
    P0 DecimalAmount MUST NOT be a case of Variant. The DecimalAmount page on lib.docs.virtufin.com calls itself "the 6th case" of Variant, and the Variant page treats it as a Variant case in some places — but DecimalAmount is a separate type with different invariants (precision-as-value, checked arithmetic, currency-aware operations like Cash). Embedding it as a Variant case is wrong: a Variant is a value-holder with implicit conversion semantics, a DecimalAmount is a domain primitive with its own arithmetic and currency logic. The two should be siblings, not nested. Remove all references that treat DecimalAmount as a Variant case. Update the DecimalAmount page to drop the "6th case" framing. Update the Variant page to remove DecimalAmount from its case list, class diagram, and pattern-matching example. The cross-cutting spec (or the core data types spec) should clarify that DecimalAmount is a sibling type, not a Variant case. The conversion pattern is DecimalAmount <-> Variant (with explicit .ToVariant() / .ToDecimalAmount()), not inheritance.
    P0 Long implicit-conversion example is wrong: 1_000_000_000_000L does NOT fit in Int32 (Int32.MaxValue is 2,147,483,647). The doc says "fits, but read as int32" which silently truncates. For a financial library with checked arithmetic, this is a potential silent data loss bug. Either fix the example (use a value that fits, like 100L) or fix the behavior (use Int64 for long coercion). The current implementation silently narrows, which is unacceptable for financial values.
    P1 IRegistry.GetValue<V> return type is ambiguous — V? GetValue<V>(IIdentifier id) where V : struct but the usage example calls it without null-checking. Document the null semantics explicitly ("null when entity not found, or when the value provider returns null"). Show a null-check pattern.
    P1 NatsObservable is a library-level direct connection, but the cross-cutting spec forbids direct pub/sub access. The lib docs don't mention this constraint. Add a note: "Workers running inside WorkManager must use the API's Pubsub.Subscribe RPC rather than connecting to NATS directly."
    P2 ValkeyObservable uses keyspace notifications which require explicit Redis/Valkey configuration (notify-keyspace-events KA) not mentioned in the docs. Add a "Prerequisites" or "Setup" section calling out the keyspace notification requirement.
    P2 The execution algebra docs (IExecutor) are thin — no usage example, no diagram, no worked scenario for DeterministicExecutorBase. Add a worked example page similar in depth to the DecimalAmount or Variant pages.
    P2 Currency only supports 12 ISO codes; the list isn't published. Publish the explicit list of 12 codes. Operators need to know which are supported.
    P3 No testing or correctness guarantees are documented for a financial library with checked arithmetic. Document the test suite in the Development page: property-based tests for DecimalAmount, round-trip tests for Variant FlatBuffers across language boundaries, etc.

    virtufin-openspec (specs.docs.virtufin.com)

    Priority Finding Remediation
    P0 The Worker Management spec still contains a full Distributed Coordination requirement with four scenarios (lock acquisition with fencing tokens, lock contention with retry, dead letter on exhausted retries, stale lock theft). But the WorkManager documentation site shows group coordination has been removed entirely from the implementation. Either reintroduce group locking to the WM implementation (matching the spec), or update the spec to reflect the competing-consumer model from the horizontal-scalability requirement as the coordination mechanism. Currently the spec and impl disagree.
    P0 Two specs referenced by the cross-cutting spec — pubsub-topics/spec.md and scenarios/spec.md — describe topic patterns, CloudEvent envelope contracts, scenario ID conventions, state-key taxonomy, and migration rules. Neither appears in the navigation sidebar or the home page specs table. Publish both specs on the site. Add them to the navigation, the home page specs table, and the dependency map.
    P1 The API Gateway spec links to a .md file directly — specs/apigateway.md rather than specs/apigateway/. This is the same broken .md extension link pattern that previously affected the WorkManager site. Convert to a directory path (specs/apigateway/) like every other spec.
    P2 NATS appears on the home page architecture diagram as an external source alongside Binance and Alpaca. NATS appears nowhere in any of the three service documentation sites — no NATS Dapr component, no NATS pub/sub adapter, no NATS client in any service's configuration. Either mark NATS as planned (a future integration not yet implemented) or remove it from the diagram. The current state is misleading.
    P2 The Sync vs Async Audit and Proto-to-Client Mapping specs appear in the nav but not in the home page specs table. Add them to the table or remove them from the nav.

    virtufin-common (the shared infrastructure repo)

    Priority Finding Remediation
    P2 The docs-common.yaml workflow's permissions: contents: read, packages: read is correct for checkout but may need pages: write if the deploy step uses gh-pages branch pushes. Verify the workflow can push to the gh-pages branch. If GH_PAGES_SSH_KEY is the auth, confirm it has write access.

    Summary of the review

    The platform documentation has matured substantially. The remaining items are all small: one duplicate section, two prose inconsistencies in WebSocketManager, one missing cache invalidation strategy, one security callout for native DLL workers (mostly done — the worker source now carries the caveat), one docker-compose port bug, two missing referenced specs, one broken .md link, and one missing Dapr version statement on two sites. Everything structurally significant from the original review is resolved.

    Highest priority cross-team fixes (in order):

    1. virtufin-openspec: resolve the group-lock spec-vs-impl divergence (P0).
    2. virtufin-dotnet: remove the claim that DecimalAmount is a Variant case. The DecimalAmount page should drop the "6th case" framing; the Variant page should remove DecimalAmount from its case list, class diagram, and pattern-matching example. The two should be sibling types, not nested. (P0 — architectural correctness.)
    3. virtufin-api: add a reflection cache TTL/invalidation endpoint (P0).
    4. virtufin-workmanager: announce the group-removal breaking change in the release notes; add the native-DLL security warning.

    Everything else is P1 or P2 — should be tracked but is not blocking.
